# Decisions

The decisions that govern the feature platform. These are settled; the [architecture](architecture.md) and the [phase folders](README.md#delivery-phases) implement them.

| 14  | Feature dependency provisioning   | A feature **provides** its own feature-specific deps via a fluent options builder (host supplies config values, feature registers, fail-fast); **shared** infra clients stay host-registered and the SDK **asserts** them at startup.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |

| 17  | Connection-event orchestration    | **`PlayerConnected` / `PlayerIpResolved` stay a single platform-owned core orchestration handler each** — they are **not** decomposed into independent pipeline handlers, because the real code has genuine coupling (GeoIP enrichment feeds the VPN guard and the welcome; the welcome is **suppressed when the guard is destructive**, e.g. a VPN kick). The core handler runs a **fixed sequence** and calls **feature-contributed collaborators** — `IConnectionEnricher` (platform GeoIP), `IConnectionGuard` (AutoAdmin VPN + VPN-detected tag), `IProtectedNameEnforcer` (AutoAdmin), `IConnectionGreeter` (Welcome Messages) — each with a **no-op SDK default** and exactly **one active implementation** (flag-gated replace). VPN Protection is therefore an `IConnectionGuard`, **not** an `IServerEventHandler`. Chat moderation (decision 15) is unaffected — it stays an independent `IServerEventHandler<ChatMessageEvent>` because chat has no such coupling. |

## Deferred governance: settings-contract guidance reconciliation

A **documentation/governance step**, triggered explicitly by the requester — no code. It brings the org instruction files in line with the feature-owned settings model (decisions 12–14) **as that model actually lands**, without getting ahead of the code.

**Why it is gated.** Today `XtremeIdiots.Portal.Settings.Contracts.V1` is the **canonical** owner of typed settings contracts, with **validate-on-write in `portal-repository`**. That is baked into the org guidance and is **correct for the current, un-migrated code**. Flipping the guidance to "feature-owned / structural-only" before the code moves would (a) misdescribe the live codebase and (b) make the `code-review` agent stop flagging genuine violations. So the guidance flip **lags the code, namespace by namespace**.

**Gate (do not start until all true):**
- The SDK settings seams (`IFeatureSettingsResolver`, `StructuralSettingsValidator`, feature-owned contracts) are shipped and frozen (Phase 0 + the Maps/AutoAdmin pilots).
- At least one feature has actually **relocated a settings contract** into its `.Abstractions` package and **retired** the central copy (first occurrence: AutoAdmin, [phase-4 §4.D](../portal-features-phase-4/retirement-plan.md)).
- `portal-repository` is validating feature namespaces **structurally only** ([phase-0 §2.D](../portal-features-phase-0/part-2-integration.md)).

**Framing (per namespace).** Rewrite the guidance so it states, at any point in time, the **true** split: which namespaces are still **platform-owned** in `Settings.Contracts.V1` (typed, validated in the repository) versus which are now **feature-owned** (contract + validator in the feature `.Abstractions`, semantic validation at the writer). A namespace only moves to the "feature-owned" column **after** its contract has migrated and its central copy has been removed. Run this in **lockstep** with each feature's retire phase, or **batched** once several features are done.

**Files to update:**

*Central (3):*
- `.github-copilot/.github/copilot-instructions.md` — the **Platform Settings Contracts (Portal Repos)** section: replace "canonical typed contracts are in `Settings.Contracts.V1` (owner: `portal-repository`)" with the **split model** — platform namespaces stay in the (repurposed) platform `Settings.Contracts.V1` package; migrated feature namespaces are feature-owned; the repository validates feature namespaces **structurally only** and keeps typed validation for platform namespaces; semantic validation for feature namespaces runs at the **writer** (`portal-web`). Keep the `ChatCommands.Abstractions.V1` "compatibility-only" line.
- `.github-copilot/.github/instructions/metadata.copilot-instructions.instructions.md` — the settings-contract ownership bullets: reword to the split model so **generated** repo copilot-instructions describe it correctly.
- `.github-copilot/.github/agents/code-review.agent.md` — the settings guardrail: replace "continued canonical use of `Settings.Contracts.V1` for typed settings contracts/validators" with checks that match the migration state: (1) **migrated** feature namespaces use the feature-owned contract in `.Abstractions` (not a re-introduced central copy); (2) `portal-repository` still validates **structurally only** for feature namespaces (no feature package reference); (3) **platform** namespaces still use the platform `Settings.Contracts.V1` package; (4) semantic validation for feature namespaces sits at the writer. Keep the `ChatCommands.Abstractions.V1` compatibility check.

*Per-repo (~12, the "Platform Settings Contracts" sections):* `copilot-instructions.md` **and** `AGENTS.md` for `portal-repository`, `portal-web`, `portal-server-events`, `portal-server-agent`, `portal-servers-integration`, `portal-sync`. Reword each to the split model, scoped to what that repo does (e.g. `portal-repository` = structural-for-features + typed-for-platform; `portal-web` = writer-side semantic validation + section shells; the worker/API repos = consume feature-owned contracts for their namespaces).

**Do / don't:**
- ✅ Move a namespace's guidance to "feature-owned" **only after** its contract has migrated and the central copy is removed.
- ✅ Keep the platform-namespace typed-validation guidance (still real for `Shared` / `Agent` / `ServerList` / transport-config namespaces).
- ✅ Update the three central files and the per-repo sections **in the same pass** so the `code-review` agent and the repo instructions never disagree.
- ❌ Do **not** flip everything to feature-owned in one go while contracts are still central.
- ❌ Do **not** remove the `ChatCommands.Abstractions.V1` compatibility-only guidance here — its shim-removal is gated separately.

**Acceptance:**
- Every guidance file describes the model that **matches the actual code state** at the time of the edit.
- `code-review.agent.md` flags settings violations appropriate to **migrated vs un-migrated** namespaces.
- A grep of the estate shows no per-repo "Platform Settings Contracts" section still asserting blanket `Settings.Contracts.V1` canonical ownership for namespaces that have migrated.

## Definition of done (every PR in the programme)

- Build + tests + `dotnet format --verify-no-changes` green in every touched repo.
- Characterization / Playwright parity proven for the touched surface.
- No feature reference leaked into `portal-repository`.
- Features consume shared host clients via DI; feature-specific deps via the options builder; no host-config reads in features.
- Scheduled jobs wrapped in `IJobTelemetry`; timers have paired manual HTTP triggers.
- Cutover is flag-gated; exactly one path runs; rollback verified.
- SDK contract changes follow **package-first-then-consume** and were surfaced at planning (NuGet gate); **after the Phase 4 freeze** they are **additive-only** (before it, the walking-skeleton SDK may still change shape).
- `code-review` sub-agent run; High/Medium findings resolved.

## Success criteria

- Adding a new chat command or a feature like VPN Protection is **one PR in one repo** plus a version bump, with **zero edits to shared Razor or host wiring** beyond an `AddXxxFeature*()` line.
- Each host's line count **drops** as features move out; hosts become composition shells.
- A feature can be **unit-tested in isolation** using the SDK `.Testing` fakes, without spinning up a host.
- **Game applicability, reconciliation ordering, and permission definitions travel with the feature** — adding a game, a reconciliation job, or a permission is a change in the feature repo, not in a central monolith.
- **Every migration is reversible fast** — a feature flag toggles legacy ↔ new (flag flip + host restart, no redeploy), and the SDK core is frozen at `v1.0` after **Phase 4** so subsequent feature work rarely touches it.
