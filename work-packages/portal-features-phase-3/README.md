# Phase 3 — AutoAdmin Feature: Build & Side-by-Side (Executable Plan)

The **execute-it-verbatim** plan for migrating the **AutoAdmin** automated-enforcement guard rails — **VPN Protection + Chat Moderation + Protected Names** — into one repo and running it **side-by-side** with the legacy in-host implementation behind a feature flag. **Legacy is not removed here** — that is [Phase 4](../portal-features-phase-4/README.md).

> Design context: [../portal-features-spec/architecture.md](../portal-features-spec/architecture.md) and the AutoAdmin grouping in [../portal-features-spec/feature-catalog.md](../portal-features-spec/feature-catalog.md). Prerequisite: **Phase 0 complete** (SDK published, hosts on the SDK seams with the full events pipeline; the connection collaborator contracts exist) and ideally **Phase 1/2** done (Maps proved the package pattern). The SDK is **not yet frozen** — Phase 3 consumes the latest `0.x` and **adds the tag substrate as a pre-freeze SDK change** (the `v1.0` freeze is Phase 4).

## What Phase 3 delivers

- **Part 1 — build & publish `portal-feature-autoadmin`** ([part-1-feature-build.md](part-1-feature-build.md)): `.Abstractions` / `.Web` / `.Processing` containing the VPN, moderation, and protected-names code moved out of `portal-server-events` and `portal-web`, plus a non-packable feature-owned Playwright project using the SDK reference host. **Feature browser tests are part of the NuGet publish gate.**
- **Part 2 — integrate behind `Feature.AutoAdmin.V2`** ([part-2-host-integration.md](part-2-host-integration.md)): **three** hosts (`portal-server-events`, `portal-web`, `portal-repository-func`) register the packages flag-gated, side-by-side with legacy. Portal-web Playwright is restricted to discovery/composition, real policy/layout, feature-flag parity, and the small shared-shell visual suite; AutoAdmin workflows remain owned by the feature repo.

**Corrections / nuances baked in (verified in code):**
- **VPN runs on BOTH `PlayerConnected` and `PlayerIpResolved`** today, and is implemented as the **`IConnectionGuard` collaborator** on the platform-owned connect/ip-resolved orchestration — **not** an `IServerEventHandler` (decision 17). The guard folds in the VPN-detected tag write + the VPN kick and sets `GuardWasDestructive` (which suppresses the welcome). The standalone `VpnProtectionEvaluation` function is subsumed by the guard. **`IpAddressGuard` is shared** (IP persistence on both events) and **stays in the host** — do not move it into AutoAdmin.
- **Moderation is a passive `Observation`, ordered AFTER commands** (decision 15). `ChatModerationHandler` (a genuine `IServerEventHandler<ChatMessageEvent>`) runs at `Order = 260` (after chat-command dispatch at 250) and **has no effect on other handlers** — it records an `Observation` admin action (the handler returns `Task`). Keep the `EventIngest.ChatToxicityDetection` flag check and the new-player/`ModerateChatTag` cost gate. Do **not** make moderation gate commands; that is not current behaviour.
- **AutoAdmin owns a reconcile job + uses the core tag substrate** (decision 16). It owns `ReconcileVpnDetectedTags` (`Set="PlayerTags"`, `Phase=Reconcile`, hosted by `portal-repository-func`) and reads `ModerateChatTag`, both via the core `IPlayerTagService`. **Prerequisite:** the tag substrate (`IPlayerTagService` + `ITagDefinitionContributor` + `AddReconciliationJob`) is a **pre-freeze SDK addition** — build + publish it into the SDK **before** this phase (NuGet dependency gate).
- **Settings contracts are feature-owned** (decision 13). Settings persist as `namespace` + opaque JSON, so the contract is just a per-feature deserialization convenience: AutoAdmin owns the `vpnProtection` / `moderation` **contract types + validators + section UI + runtime handlers**. During side-by-side it ships a **wire-compatible copy** so persisted JSON deserializes under both paths; Phase 4 deletes the central `Settings.Contracts.V1` copies.
- **`ContentSafetyClient` is feature-provided** — `AutoAdmin.Processing` registers it from host-supplied config via `AddAutoAdminFeatureProcessing(opts => opts.WithContentSafety(endpoint, credential).WithNewPlayerWindowDays(days).WithBotAdminId(botAdminId))` (fail-fast if moderation is enabled without it). The `ContentSafety:*` config section is consumed by **moderation** (client + thresholds + the **new-player window `ContentSafety:NewPlayerWindowDays`** cost gate) **and** Protected Names (`ContentSafety:BotAdminId`), so the options builder must carry **both `NewPlayerWindowDays` and `BotAdminId`** (the feature cannot read host `IConfiguration`). The host stops registering the client once the flag is on.
- **Moderation analytics / dashboard trends stay in `portal-web`** — `AnalyticsController` `global/moderation` and the dashboard moderation tile are the **Analytics** feature (read/UI), **not** AutoAdmin.
- **`Players.ProtectedNames.Write`** keeps its `Players.*` claim-type string (unchanged) even though the capability now lives in AutoAdmin.

## Main risk to watch

The **VPN/moderation settings UI is woven into the shared `GlobalSettings` / `GameServers` pages** (strongly-typed `VpnProtection` / `Moderation` view-model properties + validators), unlike Maps' dedicated controllers. Extracting them into AutoAdmin `ISettingsSection`s means moving that binding/validation into the sections. Phase 0 rendered these namespaces as in-host `ISettingsSection`s; Phase 3 **moves those sections** to the package. Treat the settings-section extraction as the highest-risk step: gate the section's validation and save/load workflows in the feature repository, then gate real shared-page composition and off/on parity in `portal-web`.

## Golden rules

- No git write ops / no secrets unless asked; follow each repo's `AGENTS.md`.
- Behaviour identical in both flag states; characterization + feature-owned functional Playwright + host-composition Playwright are the oracle.
- Surface the **publish gate**: finish Part 1, publish/review the packages, then Part 2. No cross-repo project references.
- Build + test + `dotnet format --verify-no-changes` green before any step is "done".
- **Exactly one path runs per environment** when the flag flips.

## Phase 3 definition of done

- `portal-feature-autoadmin` published to NuGet.org and restorable.
- AutoAdmin feature-owned Playwright proves Protected Names, profile block, both settings scopes, validation, and settings round-trip before publish.
- `portal-server-events` + `portal-web` + `portal-repository-func` reference the packages, flag-gated; **flag off = legacy, on = feature**, both behaviourally identical (characterization + feature-owned functional Playwright + host-composition Playwright), including moderation ordered **after** command dispatch (observation-only) and the tag-reconcile ordering.
- `Feature.AutoAdmin.V2` enabled in **dev** and **prd** and soaked, no regressions.
- Legacy VPN/moderation/protected-names code **still present** and working when the flag is off.
- `code-review` sub-agent run per repo; High/Medium findings resolved.
