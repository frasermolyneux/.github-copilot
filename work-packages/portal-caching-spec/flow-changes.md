# Portal Caching — Functional Flow Changes

The specific caching/functionality changes per API and consumer, and the phase each lands in. Architecture and rules are in [spec.md](spec.md); execution detail is in the phase folders.

| FC           | Change                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | Lands in                                     |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| **FC-1**     | `portal-servers-integration` `QueryController.GetServerStatus` becomes a **staleness-gated read-through** over LiveStatus (read via the Repository API `LiveStatus.V1`): serve the stored snapshot when `age < acceptableStaleness` (default **60s**; a force-refresh passes **0**), else issue a live RCON/UDP query and return it (**not** written back to LiveStatus; a short per-instance **L1** may coalesce repeated stale-misses). **Contract change:** `IQueryApi.GetServerStatus` gains a staleness/force-refresh parameter (published in the Phase 3 client), and `QueryController` takes a new dependency on the Repository `ILiveStatusApi`. Replaces the per-instance 300s `IMemoryCache`. | Phase 3 Part 1                               |
| **FC-2**     | Hot reference reads (`GetGameServer`, game types, maps, rotations) are cached client-side (L1) via the API clients' default policies.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Phase 2/3 client defaults + consumer rollout |
| **FC-3**     | Ad-hoc controller `IMemoryCache` blocks (`QueryController`, `FileBrowseController`, `ConnectedPlayersController`, `MapRotationsController`, `ServerAdminController`, `BannersController`) are replaced by the declarative `.WithCaching(...)` policy model.                                                                                                                                                                                                                                                                                                                                                                                                                                             | Phase 2/3 consumer rollout                   |
| ~~**FC-4**~~ | **Dropped.** A shared-L2 player-id cache was considered and rejected: the events processors cache `{ PlayerId, Tags }` **together** (via `GetPlayerByGameType(..., Tags)`), and Tags are **mutable authorization data** — a shared long-TTL cache would serve stale tags. The existing per-instance ~15-min L1 is **retained unchanged**.                                                                                                                                                                                                                                                                                                                                                               | — (removed)                                  |
| **FC-5**     | `portal-servers-integration` `FileBrowseController` FTP directory listing is standardised via the policy model as a per-instance **L1** cache (30s, `ftp:{gameServerId}:{sha256(path)}`), invalidated on upload/delete. Low-frequency admin op — no shared-account dependency.                                                                                                                                                                                                                                                                                                                                                                                                                          | Phase 3 Part 1                               |
| **FC-6**     | Repository API adds **server-side cache-aside + tag eviction** for `GetGameServer(id)` (`gameserver:{id}`), evicted in the create/update/delete handlers.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | Phase 2 Part 1                               |
| **FC-7**     | Game-server N+1 loops are batched: `MapRotationsController` (portal-web) uses `GetGameServers(null, ids, …)` once. **Maps have no batch-by-id** — the `GetMap(mapId)` loops (portal-web `MapRotationsController`, portal-sync `ResolveMapNames`) instead rely on the client `GetMap` L1 default policy to de-dupe repeated ids.                                                                                                                                                                                                                                                                                                                                                                         | Phase 2 (portal-web, portal-sync)            |
| **FC-8**     | Repository API caches the four dashboard aggregations (`GetDashboardSummary`, `GetAdminLeaderboard(30)`, `GetModerationTrend(30)`, `GetServerUtilization`) server-side with a 60–120s TTL.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Phase 2 Part 1                               |
| **FC-9**     | Repository API caches the **resolved** per-server settings document (`settings:{gameServerId}:{namespace}`), evicted on `UpsertConfiguration` (server+namespace; global-namespace write evicts all servers).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Phase 2 Part 1                               |

## Additional Phase 2 Part 1 changes

- Provision the **shared cache storage account** in `portal-core` and grant `Storage Table Data Contributor` to the **Repository API** managed identity (the only service that touches it directly; `portal-server-events` writes LiveStatus **through** the Repository API, so it needs no direct grant).
- **Move LiveStatus** (status + players) onto the shared cache account (ephemeral data; no migration).
- **Extend the existing `GetConnectedPlayers`** endpoint (already paged: skip/take + filters) with **server-side search + sort**, so `portal-web` pages/filters/sorts server-side and drops its full-table fetch+cache.

## Consumer rollout

| API                               | Consumers                                                                                                                          |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| Repository API (Phase 2)          | `portal-web`, `portal-servers-integration`, `portal-server-events`, `portal-server-agent`, `portal-sync`, `portal-repository-func` |
| Servers Integration API (Phase 3) | `portal-web`, `portal-sync`, `portal-server-agent`                                                                                 |

Each consumer bumps the published client package, opts into library defaults (`.WithCaching(c => c.UseLibraryDefaults())`), applies any overrides, and retires superseded ad-hoc caches. RCON/mutation endpoints remain `NotCached`.
